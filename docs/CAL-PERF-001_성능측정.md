# CAL-PERF-001 성능 측정

목표(정의서 비기능 요구): **처음 켜기 2초 이내, 월 이동 100ms 이내**. 측정 도구는 `tools/measure_perf.py`, 앱 쪽 측정 모드는 `FlowCalendar.exe --benchmark`.

## 방법

1. 임시 폴더에 가짜 데이터를 만든다 — **일정 450건(반복 30건 포함, 여러 날 일정 포함), 할 일 160개, 메모 30줄**. `FLOWCALENDAR_DATA_DIR`로 지정해 내 실제 데이터는 건드리지 않는다. 비교용으로 빈 데이터(처음 설치한 모습)도 잰다.
2. 앱을 `--benchmark`로 실행한다. 첫 화면이 **실제로 그려지면**(창 표시 + 동기 다시 그리기) 앱이 표시 파일을 만들고, 도구는 **프로세스를 시작한 순간부터 그 파일이 생길 때까지의 시계 시간**을 잰다. 인터프리터/Qt 불러오기, 창 만들기, 트레이·스케줄러 준비, 첫 그리기가 모두 포함된다.
3. 이어서 앱이 다음 달로 **24번** 넘기며, 한 번의 `shift_month`(DB 조회 + 칸 다시 구성) + 창 다시 그리기 시간을 잰다.
4. 표시 파일이 생기는 순간과 월 이동이 끝난 순간에 프로세스의 메모리(작업 집합 / 전용 바이트)를 읽는다.
5. 6번 반복해 첫 실행(디스크 캐시가 차가움), 이후 가운데 값, 가장 느린 값을 본다.

## 결과 (2026-10-28, 묶은 실행 파일 `dist\FlowCalendar\FlowCalendar.exe`, v1.0.0)

| 항목 | 데이터 많음(일정 450·할 일 160) | 빈 데이터 | 목표 |
| --- | --- | --- | --- |
| 처음 켜기, 첫 실행 | 1,732 ms | 1,431 ms | 2,000 ms |
| 처음 켜기, 이후 가운데 / 가장 느림 | 1,122 / 1,294 ms | 1,078 / 1,159 ms | 2,000 ms |
| 월 이동 1회, 평균 / 가장 느린 이동 | 61 / 78 ms | 19 / 32 ms | 100 ms |
| 메모리(월 이동 24번 뒤), 작업 집합 / 전용 | 197 / 151 MB | 100 / 52 MB | — |

- 설치 파일(`FlowCalendar-Setup-1.0.0.exe`) 22MB, 설치된 폴더 약 70MB.
- 개발 환경(`python -m flowcalendar`)도 비슷하다: 켜기 약 1.0초, 월 이동 평균 64ms.

## 이번에 찾아 고친 것: 월 이동이 느렸다

처음 측정에서 월 이동이 **평균 394ms, 최대 710ms**로 목표(100ms)를 넘었다. 원인은 날짜 칸이 일정 칩을 **'+N개'로 접힌 것까지 전부** 위젯으로 만들고 있던 것(이 데이터에서 한 번 이동에 약 450개). 보이는 줄만 만들고, 칸이 커져서 더 보이게 되면 그때 만들도록 바꿨다. 같은 데이터에서 **평균 64ms, 최대 81ms**로 줄었다(`calendar_view.DayCell._layout_children`, 테스트 `test_only_visible_items_get_widgets…`).

## 알아둘 점 (한계)

- 이 컴퓨터는 측정 중 사용 가능한 메모리가 1.4~2GB로 **다른 프로그램이 많이 떠 있는 상태**였다. 한가한 컴퓨터에서는 더 빠를 가능성이 크지만 확인하지 못했다.
- **재부팅 직후의 진짜 콜드 스타트는 재현하지 못했다.** 설치 직후 처음 켠 한 번은 2.3초가 걸렸다(새로 쓴 파일을 Windows가 검사하는 시간으로 보이며, 빈 데이터 기준). 이 한 번은 목표 2초를 넘었다. 이후 실행은 1초 안팎이다.
- 메모리 197MB는 데이터가 많고 월을 24번 넘긴 **측정용 상태**다. 월 이동 중에 만든 화면 부품은 이벤트 루프가 돌아야 지워지는데 측정용 반복에서는 덜 지워진다. 평소 사용(빈 데이터 약 52MB 전용)과는 다를 수 있다.
- 월 이동이 여러 번 평균보다 크게 튄 적이 한 번(첫 측정의 실행 1·6에서 168·223ms) 있었다. 다음 측정(같은 빌드)에서는 재현되지 않았고, 시스템이 바쁜 순간 때문으로 추정한다.
